
## 一、刚 `fork()` 之后：父子进程的 “相同点”

PPT 里列的这些，**在刚 `fork()` 时，子进程和父进程的 “值” 是完全一样的**：

- 代码段（`.text`）：也就是你的程序指令，父子进程执行的是同一份代码
- 数据段（`.data`、`.bss`）：全局变量、静态变量的初始值完全相同
- 栈、堆：父进程的栈帧、堆分配的内容，子进程都会复制一份
- 环境变量、用户 ID（UID/EUID）、组 ID（GID/EGID）、工作目录、信号处理方式

**注意**：这些 “相同” 只是初始值一样，**不是共享内存**，父子进程后续修改互不影响。

---

## 二、刚 `fork()` 之后：父子进程的 “不同点”

这些是父子进程天生就不一样的属性：

1. **进程 ID（PID）**：每个进程的身份证号，子进程一定是新的 PID
2. **`fork()` 的返回值**：父进程返回子进程的 PID，子进程返回 0
3. **父进程 ID（PPID）**：子进程的 PPID 就是父进程的 PID，父进程的 PPID 是它的父进程（比如 bash）
4. **进程运行时间**：子进程是刚创建的，运行时间从 0 开始
5. **闹钟 / 定时器**：父进程设置的闹钟，子进程不会继承
6. **未决信号集**：父进程正在排队等待处理的信号，不会传给子进程

## 三、关键：写时复制（Copy-On-Write, COW）的真相

PPT 里提到了一个核心误区：

> 不是每次 `fork()` 都真的把父进程 0-3G 的地址空间完整复制一份！

### 什么是写时复制？

- 刚 `fork()` 时，父子进程**共享同一份物理内存页**，内核会把这些页标记为 “只读”
- 当父进程或子进程**尝试修改**其中任何一页时，内核才会为这个进程单独复制一份副本，让它修改
- 只有 “修改的页” 会被复制，没修改的页继续共享

### 好处

- 极大节省内存：如果子进程 `fork()` 后立刻调用 `exec()` 执行新程序，大部分页根本不会被修改，完全不用复制
- 效率更高：避免了不必要的拷贝开销

## 四、重点纠正：父子进程 “不共享” 全局变量！

PPT 里特意提醒了 “躲避父子进程共享全局变量的误区”，这里一定要记死：

- 父子进程的全局变量**初始值相同，但地址空间完全独立**
- 子进程修改全局变量，父进程完全看不到，反之亦然
- 它们的 “相同” 只是复制了初始值，不是共享内存

你可以用这段代码验证：

c

运行

```cpp
#include <stdio.h>
#include <unistd.h>
int g_val = 100;

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        // 子进程修改全局变量
        g_val = 200;
        printf("child: g_val = %d\n", g_val);
    } else {
        sleep(1); // 等子进程修改完
        printf("parent: g_val = %d\n", g_val);
    }
    return 0;
}
```

运行结果一定是：

plaintext

```
child: g_val = 200
parent: g_val = 100
```

父进程的变量根本不会变，因为它们的地址空间是独立的。

## 五、父子进程真正 “共享” 的资源

只有这两类资源，父子进程是**真・共享**的：

1. **文件描述符**
    
    - 父进程打开的文件描述符，子进程会继承一份引用
    - 父子进程共享同一个文件偏移量，比如父进程 `write()` 后，子进程 `read()` 会接着读
    
2. **`mmap` 建立的共享映射区**
    
    - 如果用 `mmap` 创建了 `MAP_SHARED` 映射区，父子进程会共享同一块物理内存
    - 这是进程间通信（IPC）的一种方式，修改后双方都能看到
    

---

## 六、一句话总结

- `fork()` 刚完成时，父子进程 “看起来” 什么都一样，是因为**复制了初始值 + 写时复制共享内存**
- 一旦任何一方修改数据，写时复制就会触发，父子进程的地址空间就彻底独立了
- 真正跨进程共享的，只有文件描述符和 `MAP_SHARED` 映射区
