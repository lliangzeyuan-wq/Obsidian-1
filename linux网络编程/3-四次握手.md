## 一、四次握手的核心流程（对应你图里的步骤）

TCP 是**全双工**协议，双方都可以独立发送和接收数据，所以关闭连接时，双方都需要单独关闭自己的发送通道，因此需要四次交互。

### 四次握手完整过程（对应你图里的 4 个关键报文）

表格

|步骤|方向|报文类型|核心作用|双方状态变化|
|---|---|---|---|---|
|**第一次挥手**|客户端 → 服务器|`FIN`（结束报文）|客户端发送完数据，主动关闭自己的发送通道，不再发送数据|客户端：`FIN_WAIT_1`|
|**第二次挥手**|服务器 → 客户端|`ACK`（确认报文）|服务器确认收到客户端的 `FIN`，客户端的发送通道正式关闭（半关闭）|客户端：`FIN_WAIT_2`；服务器：`CLOSE_WAIT`|
|**第三次挥手**|服务器 → 客户端|`FIN`（结束报文）|服务器发送完数据，关闭自己的发送通道，不再发送数据|服务器：`LAST_ACK`|
|**第四次挥手**|客户端 → 服务器|`ACK`（确认报文）|客户端确认收到服务器的 `FIN`，服务器的发送通道正式关闭，双方连接完全断开|客户端：`TIME_WAIT`；服务器收到 `ACK` 后变为 `CLOSED`|

## 二、结合你的服务器代码，四次握手在哪里发生？

你的服务器里，四次握手的核心逻辑由内核完成，应用层只需要调用 `close()` 或 `shutdown()` 系统调用：

1. **客户端调用 `close()`**：内核发送 `FIN` 报文，触发第一次挥手。
2. **服务器收到 `FIN`**：内核回复 `ACK`（第二次挥手），此时服务器的 `recv()` 会返回 0，表示客户端关闭了连接。
3. **服务器处理完剩余数据后调用 `close()`**：内核发送 `FIN` 报文（第三次挥手）。
4. **客户端收到 `FIN` 后回复 `ACK`**（第四次挥手），连接完全关闭。

### 对应你代码里的关键逻辑：

- `TcpConn::handleRead()` 中，当 `recv()` 返回 0 时，说明客户端关闭了连接，服务器需要主动调用 `close()` 发送 `FIN`。
- `do_clean()` 函数会从连接列表中移除已关闭的连接，避免内存泄漏。

## 三、面试高频问题：为什么是四次挥手，而不是三次？

核心原因是**半关闭状态的存在**：

- 当客户端发送 `FIN` 后，服务器回复 `ACK`，此时客户端已经不能再发送数据，但服务器可能还有数据要发给客户端（比如响应延迟），所以服务器的 `FIN` 必须单独发送，不能和 `ACK` 合并。
- 三次握手可以合并 `SYN` 和 `ACK`，但四次挥手无法合并 `FIN` 和 `ACK`，因此必须分四次。

## 四、关键细节：`TIME_WAIT` 状态（面试必问）

客户端发送完最后一个 `ACK` 后，会进入 `TIME_WAIT` 状态，持续 2MSL（最长报文寿命，通常是 1-2 分钟），为什么要等待？

1. **确保服务器收到最后一个 `ACK`**：如果服务器没收到，会重发 `FIN`，客户端在 `TIME_WAIT` 状态下可以重发 `ACK`，避免服务器一直等待。
2. **防止旧连接的报文干扰新连接**：等待期间，旧连接的报文会在网络中消失，避免影响新建立的连接。

### 对服务器的影响：

- 服务器收到客户端的 `FIN` 后，如果不及时调用 `close()`，会处于 `CLOSE_WAIT` 状态，占用文件描述符，高并发下可能导致文件描述符耗尽。
